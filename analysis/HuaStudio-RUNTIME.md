# HuaStudio 运行时解剖（跑出来的真相）

> 样本：一次 24.8 秒的真实录制（屏幕 + 摄像头 + 麦克风），项目 ID A5C6C2B9
> 方法：读取沙盒容器里的项目产物，不是反汇编——**这是软件自己写出来的数据，比任何静态分析都准**

---

## 一、录制产物结构

~~~
Recordings/<recording-id>/
├── screen.mp4    2940×1740  H.264  4.24 Mbps  AAC 48kHz mono   24.88s
├── camera.mp4    1920×1080  H.264 11.52 Mbps                   25.08s
├── poster.jpg     封面缩略图
├── meta.json      录制元数据（含音频健康度）
├── track.json     光标轨迹 + 点击事件
├── timeline.json  app 切换时间线
├── project.json   编辑后的项目状态
└── track.json     28 KB
~~~

**关键决策：屏幕和摄像头分成两个文件录**。因为分辨率、帧率、色彩空间都不同（60fps vs 29.97fps），强行混流只会掉帧。合成留到导出阶段。这是专业做法。

  "beautify": true,

  "cfg": {
    "autoZoom": true,
    "zoomLevel": 1.6,
    "zoomSpeed": 0.9,

    "clickFx": true,
    "motionBlur": 0.08,
    "background": "slate",
    "canvasAspect": "source",
    "padding": 0.10493070083682009,
    "radius": 20,
    "shadow": 0
  },

  "camCfg": {
    "show": true, "mirror": true, "ring": true, "shape": "circle",
    "size": 0.22,
    "x": 0.2155595705605894,
    "y": 0.7829194761410788
  },

  "audio": { "micVol": 1, "sysVol": 1 },

  "segments":  [ { "s": 1500, "e": 24836.526291, "speed": 1 } ],
  "zoomSegs":  [ ... ],
  "masks": [], "layoutSegs": [], "audioSegs": []
}
~~~

### 默认值解读

| 参数 | 值 | 含义 |
|---|---|---|
| zoomLevel | **1.6** | 缩放倍率。1.6 是克制值——2.0 会晕，1.3 看不出效果 |
| zoomSpeed | 0.9 | 接近 1 但略慢，避免"弹"的感觉 |
| motionBlur | **0.08** | 极轻微拖影。大一点就糊 |
| padding | **0.1049** | 画面到边缘 10.5%，约等于 1080p 下 113px |
| radius | 20 | 圆角像素 |
| shadow | **0** | 默认无阴影！说明阴影是"风格化选项"不是默认审美 |
| cursorSmooth | 60 | 与光标采样率 63Hz 呼应 |
| background | slate | 深灰蓝，中性不抢戏 |
| canvasAspect | source | 保持原始画幅，不裁剪 |

**camCfg.size = 0.22** —— 摄像头占画面 22%（宽或高）。位置 (0.216, 0.783) 是左下角。

**segments: s=1500** —— 自动裁掉开头 1.5 秒（录制启动时的鼠标找位置、窗口切换），这是"零操作剪辑"的第一刀。

## 三、自动缩放算法（从数据反推，有硬证据）

实测一条 zoomSeg 与 4 次点击的对照：

~~~
zoomSeg.start = 21179.43 ms
zoomSeg.end   = 23813.65 ms
zoomSeg.points[0] = { t: 21629.43, x: 0.1147, y: 0.3326 }

点击事件：
  click #2  t = 21629.43  x = 0.1103  y = 0.3596
  click #3  t = 22313.65  x = 0.1191  y = 0.3055
~~~

**两个精确到 0.1ms 的关系**：

~~~
start = 第一次点击时刻 - 450 ms
end   = 最后一次点击时刻 + 1500 ms
~~~

这不是猜的，是三次数据全部吻合：

| 量 | 计算 | 实测 | 误差 |
|---|---|---|---|
| start | 21629.43 − 450 | 21179.43 | 0.00 |
| end | 22313.65 + 1500 | 23813.65 | 0.00 |

### 为什么是 450 / 1500

- **提前 450ms 开始**：人眼对"延迟响应"极其敏感。如果点下去才开始缩放，感知上是"卡了半拍"。提前 450ms 让缩放在点击**发生前**就开始推进——用户会觉得画面"懂他要干什么"。
- **延后 1500ms 结束**：点完立刻拉回原状会打断阅读。留 1.5 秒让用户看清放大后的内容。

**这两个数字就是这类产品的核心手感参数。**

### 缩放中心不等于点击位置

~~~
点击  (0.1103, 0.3596)
中心  (0.1147, 0.3326)
偏差  (+0.0044, -0.0270)
~~~

中心做了**向上偏移**（y 减小 = 画面上移）——因为点击目标通常在按钮上，而用户关注的是按钮**周围的内容**，不是按钮本身。偏移量约 0.027，在 1740px 高度上约 47px。

## 四、track.json —— 输入的原始信号

~~~json
{
  "cursor": [
    { "t": 274.78, "x": 0.5364, "y": 0.4006 },
    ... 261 个采样
  ],
  "clicks": [
    { "t": 16597.51, "x": 0.3732, "y": 0.4843 },
    ... 4 个
  ]
}
~~~

- 坐标全部**归一化到 0..1**（与分辨率解耦，换屏幕也能用）
- 光标采样 261 个 / 24.8 秒
- 采样间隔：最小 8.0ms，中位数 **15.8ms**（≈63Hz），最大 14.1 秒（用户没动鼠标，有静止压缩）

**静止压缩**是个细节：不动的时候不记录，省 90% 体积。所以 track.json 只有 28 KB。

## 五、timeline.json —— app 切换时间线

~~~json
{
  "apps": [
    { "bundleID": "com.citrolabs.ego.lite", "name": "ego lite", "t": 0 },
    { "bundleID": "dev.zcode.app",          "name": "ZCode",     "t": 1579.17 },
    ...
  ]
}
~~~

25 秒内 8 次切换，5 个不同 app。

**这是"焦点感知"的数据源**：知道用户在哪个 app 里，就能推断他在干什么，从而决定缩放区域。Screen Studio 也有类似机制，但 HuaStudio 把它显式落盘成时间线。

## 六、meta.json —— 专业级的音频健康度

~~~json
{
  "audioGaps": {
    "mic": { "endDriftMs": 8.9e-10, "holeCount": 0, "holeFilledMs": 0,
             "maxDriftMs": 8.9e-10, "maxQueueMs": 11.61, "overflowMs": 0 },
    "sys": { "endDriftMs": 4.4e-10, "holeCount": 0, "holeFilledMs": 0,
             "maxDriftMs": 4.4e-10, "maxQueueMs": 40,   "overflowMs": 0 }
  },
  "camOffsetMs": -173.25612498098053,
  "durationMs": 24836.526291,
  "width": 2940, "height": 1740
}
~~~

| 字段 | 含义 |
|---|---|
| holeCount / holeFilledMs | 音频丢包次数 + 补了多少毫秒（0 = 完美） |
| maxQueueMs | 缓冲队列峰值（mic 11.6ms / sys 40ms） |
| overflowMs | 溢出毫秒数（0 = 没爆） |
| endDriftMs | 结束时刻的漂移（1e-10 级 = 时钟对齐精确） |
| camOffsetMs | **摄像头比屏幕晚 173ms** |

**camOffsetMs = -173ms** 是硬事实：摄像头采集链路比屏幕慢约 173ms（曝光+USB/内置相机管线）。软件自动测出来并对齐。这就是为什么音画嘴型是对的——不是用户手动调的。

音频队列监控这套东西，99% 的录屏软件没有。有它才能保证"录 2 小时不掉音"。

## 七、采集规格（ffprobe 实测）

| | 屏幕 | 摄像头 |
|---|---|---|
| 分辨率 | 2940×1740（1470×918 @2x） | 1920×1080 |
| 编码 | H.264 | H.264 |
| 码率 | 4.24 Mbps | 11.52 Mbps |
| 帧率 | 60 fps | 29.97 fps |
| 音频 | AAC 48kHz 单声道 98kbps | 无 |

摄像头码率是屏幕的 2.7 倍（11.5 vs 4.2）——因为画面变化剧烈（人脸），屏幕内容静止多。**H.264 的码率自适应在这里被正确利用**。

## 八、和 Screen Studio 的对照

| 维度 | Screen Studio | HuaStudio |
|---|---|---|
| 缩放提前量 | 未知（未挖到） | **450ms** |
| 缩放退出延迟 | 未知 | **1500ms** |
| 缩放倍率默认 | 未知 | **1.6** |
| 音频漂移监控 | 有（sentry 遥测） | **本地落盘**（更透明） |
| 摄像头对齐 | 有 | **-173ms 自动测** |
| 录制分文件 | 是 | 是 |

**两个产品在工程结构上高度相似**，说明这是这个品类的正确解法，不是抄的。
